Understanding Operating Systems From kernels to security — a foundational guide for security professionals

OS Fundamentals· Security· Architecture

1. What Is an Operating System?

An operating system is the software layer that sits between your hardware and the applications you run. It's the silent mediator — managing every resource, every process, every byte of memory — so that you (and your programs) don't have to.

Think of the OS like a restaurant manager. You (the app) don't talk to the chef directly, you don't wash dishes, you don't negotiate with the produce supplier. You just place your order — and the manager makes sure it happens. If the kitchen catches fire, the manager handles it. If two tables order at the same time, the manager decides who gets attention first. That's your OS.

Core jobs of an operating system:

  • Process management — creating, scheduling, and terminating processes; managing CPU time across competing tasks. Like a traffic cop for running programs.
  • Memory management — allocating and deallocating memory, handling virtual memory, paging, and swapping. Making sure no app hogs all the RAM.
  • File systems — organizing and storing data on disk in structured ways (files, directories, permissions). Your digital filing cabinet.
  • Input/Output (I/O) — communicating with hardware devices through drivers. The translator between your software and your keyboard, mouse, GPU, etc.
  • Security — enforcing user permissions, access control, and isolation between processes. The bouncer at the club.

Without an OS, every application would need to talk directly to the hardware — managing its own CPU time, writing its own disk drivers, and negotiating network cards. The OS abstracts all of that into clean system calls. Basically, your apps would be like someone showing up to a restaurant and demanding to cook their own meal in the kitchen. The OS is there to say "sit down, I'll handle it."

2. Types of Operating Systems

Operating systems come in many flavors, each optimized for different environments and constraints.

Desktop Operating Systems

  • Windows — The dominant desktop OS. Broadest software/hardware compatibility. Also the most malware-targeted — like living in the biggest house on the block. Everyone wants to break in.
  • macOS — UNIX-based with a polished GUI. Popular in creative industries and software development. Tight ecosystem lock-in — Apple builds the whole house, including the plumbing.
  • Linux (distributions) — Open source, highly customizable. Dominant on servers, cloud, and cybersecurity workstations. The IKEA furniture of OSes — you build exactly what you want.

Mobile Operating Systems

  • Android — Linux-based, open source. Massive hardware variety. App sandboxing via SELinux and per-app UIDs. Your phone is a pocket computer that also happens to make calls.
  • iOS — UNIX-based (XNU kernel), closed ecosystem. Strong sandboxing, hardware-backed security, strict app review. Apple watches your every step — which is creepy but also why it's harder to infect.

Server Operating Systems

  • Linux (Ubuntu Server, RHEL, Debian, CentOS) — The backbone of the internet. Lightweight, command-line oriented, dominant in cloud infrastructure. If the internet were a building, Linux is the concrete.
  • Windows Server — Enterprise environments with Active Directory, Exchange, and .NET infrastructure. The office building with security badges and fluorescent lighting.

Real-Time Operating Systems (RTOS)

  • FreeRTOS, QNX, VxWorks — Designed for deterministic timing guarantees. Used in automotive (brake-by-wire), medical devices (infusion pumps), industrial control, and IoT.
  • Trade-off: Real-time guarantees often come at the cost of security features like memory protection and ASLR. Your car's braking system can't wait 200ms because the OS is busy checking for updates.

Embedded / Firmware

  • Tiny, purpose-built OSes that run on microcontrollers. Often no MMU, no privilege separation, no filesystem. Think: your router, your smart lightbulb, your car's ECU.
  • From a security perspective, these are often the weakest link — hard to patch, minimal defenses. That smart kettle in your kitchen is a Linux box with no firewall. Let that sink in.

3. The Kernel — The Heart of the OS

The kernel is the core of the operating system. It runs with the highest hardware privilege level and has complete control over everything. Everything else — every application, every service, every driver — sits on top of it. Imagine a nightclub bouncer who has the master key to every door, access to the panic room, and the authority to throw anyone out instantly. That's the kernel.

What the kernel does:

  • Manages CPU scheduling — who gets to run and for how long
  • Handles memory allocation and virtual memory — making sure processes don't step on each other's toes
  • Manages system calls from user-space programs — the official "ask the kernel for something" channel
  • Controls hardware through device drivers — your app says "I want to save this file" and the kernel talks to the SSD
  • Enforces security policies — the bouncer checking IDs at the door

Kernel Architectures

Type Design Examples Security Impact
Monolithic Entire OS runs in kernel space (file systems, drivers, networking, all in one big blob) Linux, BSD Fast, but one driver bug crashes the whole system. If a waiter sneezes in the kitchen, the entire restaurant closes.
Microkernel Minimal kernel — only IPC and basic scheduling. Drivers and services run in user space. Minix, QNX, seL4 Isolation is excellent. A driver crash doesn't take down the OS. If the waiter sneezes, only that table is affected.
Hybrid Microkernel philosophy but runs some services in kernel space for performance Windows NT, macOS XNU Balance of performance and stability, but inherits risks from both approaches.

Why it matters for security: A vulnerability in a monolithic kernel (like a Linux privilege escalation bug) gives an attacker ring-0 access — total control. It's like giving the burglar the master key to every room in the building. Microkernels limit the blast radius — even if someone breaks in, they're stuck in one room. For pentesters, knowing the kernel type of your target shapes your whole exploitation strategy.

4. How an OS Manages Resources

Process Scheduling

The OS decides which process gets CPU time and for how long. Scheduling algorithms (Round Robin, Completely Fair Scheduler, priority-based) balance throughput, latency, and fairness.

Relatable example: Ever been on a Zoom call while your browser has 47 tabs open, Spotify is playing, and Slack is loading a GIF? The OS is constantly juggling — giving each app a tiny slice of CPU time so fast that your brain perceives it as everything running simultaneously. It's like a stage magician spinning plates — drop one and the whole act falls apart.

From a security perspective, scheduling can leak information through timing side channels. If you can measure exactly how long a process takes to respond, you might infer what it's computing. This is how Spectre and Meltdown worked — exploiting the CPU's speculative execution to peek into kernel memory.

Memory Management

Modern OSes use virtual memory — each process gets its own address space, mapped to physical memory through page tables. This provides:

  • Isolation: Process A cannot read Process B's memory. Your browser can't see your password manager's data.
  • Paging: Memory is divided into fixed-size pages; unused pages are swapped to disk. Ever had your laptop slow to a crawl because you had too many things open? That's swapping — the OS is frantically moving data between RAM and your SSD.
  • ASLR (Address Space Layout Randomization): Randomizes where code and data are loaded — makes buffer overflow exploitation harder. Imagine trying to pick a lock that changes its pin positions every time you blink.

File Systems

Each OS uses its own native filesystem, each with different performance, reliability, and security characteristics:

Filesystem Used By Key Features
NTFS Windows Journaling, permissions (ACLs), encryption (EFS), compression, large file support
ext4 Linux Journaling, extended attributes, backward compatibility, large volumes
APFS macOS / iOS Snapshots, cloning, encryption, space sharing, optimized for SSDs
FAT32 / exFAT Cross-platform / USB Widely compatible, no permissions, no journaling, limited file size (FAT32: 4GB max — try saving that 4K movie and watch it fail)

Fun fact: Your USB drive is probably exFAT or FAT32. That means it has no built-in permissions. Plug it into anyone's computer and they can read everything. That's why you encrypt your USB sticks, right? Right?!

Device Drivers and I/O

Drivers translate generic OS commands into hardware-specific instructions. Think of them as translators at the United Nations — the OS speaks one language, your GPU speaks another, and the driver makes sure they understand each other.

In monolithic kernels, drivers run in kernel space — a buggy driver can crash the entire OS or, worse, introduce a privilege escalation vector. Ever had a blue screen out of nowhere? Probably a driver. In microkernels, drivers run in user space, so a crash just restarts the driver. Elegant, but slower.

5. User Mode vs. Kernel Mode

This is the most important security boundary in any modern OS. CPUs provide at least two privilege levels:

  • User Mode (Ring 3 on x86): Applications run here. Restricted — no direct hardware access, no system table manipulation, restricted address space. You're a guest in a hotel — you can't go into the staff-only areas or touch the main electrical panel.
  • Kernel Mode (Ring 0 on x86): The OS runs here. Full hardware access, all memory visible, all CPU instructions available. You're the hotel manager with keys to every room, the boiler room, and the safe.

What happens when an app crashes: The OS kills the process, frees its memory, and moves on. No problem. You've seen it — "This tab has crashed" in Chrome. That's user mode doing its job. One guest got drunk, security threw them out, the party continues.

What happens when the kernel crashes: The entire system halts. Blue screen. Kernel panic. System reboot. That's the hotel manager falling down the stairs — now nobody can do anything.

How Privilege Escalation Attacks Work

Every privilege escalation exploit is about crossing the user-mode-to-kernel-mode boundary without authorization. It's the guest at the hotel finding a way to clone the manager's keycard.

Common vectors:

  • Kernel buffer overflows — writing past a buffer in kernel space to overwrite a return address. Like overflowing a glass of water on purpose to short-circuit the electrical panel.
  • Dirty Pipe / Dirty Cow — race conditions in kernel memory handling that let a user process write to read-only files. The OS blinked for a split second, and in that blink, you swapped something out.
  • ioctl abuse — sending malformed control codes to device drivers. The kernel asks "what do you want to do with this device?" and you answer in SQL injection.
  • TOCTOU (Time-of-check-time-of-use) — racing a kernel syscall between permission check and actual operation. The bouncer checks your ID, you seem fine, but by the time you walk in, you've swapped your ID with someone else's.

The goal is always the same: get NT AUTHORITY\SYSTEM on Windows, root on Linux, or the equivalent on any OS. Full access. The master key.

6. The Boot Process — How an OS Actually Starts

Most people click the power button and wait for the login screen. But between those two moments, a chain of events happens that's fascinating — and critical for security.

Think of booting like waking up a sleeping giant. You don't just yell "WAKE UP!" and expect it to run a marathon. You start with a whisper.

The Boot Chain

  1. Power On → UEFI/BIOS — The CPU wakes up, looks at a fixed memory address, and finds the firmware (UEFI or BIOS). This is the giant blinking "who am I, where am I?" moment.
  2. POST (Power-On Self Test) — The firmware checks that your RAM, CPU, and basic hardware are functional. If your RAM is dead, you get beep codes instead of a boot screen.
  3. Bootloader — The firmware finds a bootable device (your SSD, a USB stick, a network boot) and loads the bootloader. On Linux, that's GRUB. On Windows, it's the Windows Boot Manager. This is the first software that actually "runs."
  4. Kernel Initialization — The bootloader loads the kernel into memory and hands over control. The kernel starts setting up memory management, scheduling, and drivers. This is the giant sitting up and opening its eyes.
  5. Init System — The kernel starts the first user-space process (PID 1). On modern Linux, that's systemd. On Windows, it's smss.exe. This process then launches everything else — login screen, services, your desktop.

Why This Matters for Security

Every step in the boot chain is a potential attack point:

  • Firmware attacks — Malware can infect your UEFI firmware (like the BlackLotus bootkit). It survives reinstallations, disk swaps, even new OS installations because it lives below the OS entirely.
  • Bootloader attacks — If an attacker can modify your bootloader, they can load a malicious kernel or disable security features.
  • Bootkits — Malware that loads before the OS, intercepting kernel calls and hiding itself from antivirus. The ultimate "I'm not touching you" attack.

Defenses: UEFI Secure Boot verifies that the bootloader is signed by a trusted key. TPM measures each step of the boot process (measured boot) and can refuse to decrypt your disk if anything has been tampered with. BitLocker, FileVault, and LUKS all tie into this chain.

Real-world example: In 2023, the BlackLotus UEFI bootkit made headlines because it bypassed Secure Boot on fully patched Windows systems. It didn't infect Windows — it infected the firmware before Windows even loaded. Antivirus couldn't see it because it was hiding underneath the entire OS. The fix required a firmware update from motherboard manufacturers, not a Windows patch.

7. System Calls — How Programs Talk to the OS

You're writing code. You want to read a file. You call open(), read(), close(). Simple, right? But behind the scenes, something remarkable happens — your program crosses from user mode into kernel mode.

Think of system calls like filling out a government form. You (the app) don't walk into the server room and pull the file yourself. You fill out Form 83-B ("Open File Request"), submit it through a tiny slot, and the kernel processes it for you. A few milliseconds later, you get your data back.

How It Actually Works

  1. Your program calls open("file.txt", O_RDONLY)
  2. Your C library (glibc on Linux, msvcrt on Windows) prepares a syscall
  3. The CPU switches from Ring 3 (user) to Ring 0 (kernel) using a special instruction — syscall on x86-64, int 0x80 on older Linux
  4. The kernel looks up the syscall number in a table (the syscall table) and runs the appropriate function
  5. Result is passed back, CPU switches back to Ring 3
Example — syscall flow on Linux x86-64:

; User wants to write "hello" to stdout
mov rdi, 1 ; fd = stdout
mov rsi, msg ; buffer = "hello"
mov rdx, 5 ; count = 5
mov rax, 1 ; syscall number for write()
syscall ; 🚀 crossing into kernel space

Why This Is a Security Nightmare (and also a defense)

The syscall table is stored in kernel memory. If an attacker can modify it — say, replace the open() handler with a malicious version — they can intercept every file access on the system. This is exactly what kernel rootkits do.

On the flip side, security tools like EDRs (Endpoint Detection and Response) also hook syscalls. When you try to CreateProcess() on Windows, the EDR intercepts it, checks if the binary is malicious, and either allows or blocks it. Same technique, different intentions.

Relatable example: Imagine you work in a building where every door has a guard. To open any door, you fill out a form, slide it under the door, and the guard opens it for you. That's a system call. Now imagine someone replaces the guard with their friend. Suddenly every room in the building is accessible — and nobody knows because the form looks the same. That's a syscall hook.

Real-world example: The Stuxnet rootkit used syscall hooking to hide its files from antivirus. When Windows asked "is this file present on disk?", Stuxnet's hook intercepted the syscall and replied "nope, nothing here" — even though the file was sitting right there.

8. OS Defensive Mechanisms

Modern operating systems aren't just sitting there waiting to be exploited. They've built up layers of armor over the decades, each one a response to a real attack. Here's what they do and how attackers (and pentesters) get around them.

The Big Four

Defense What It Does Bypass Techniques
DEP / NX (Data Execution Prevention / No-Execute) Marks memory pages as either executable or writable — never both. You can't inject shellcode onto the stack and run it because the stack isn't executable. ROP (Return-Oriented Programming) — chain together tiny snippets of existing code (gadgets) to do what you want without executing new code. Like building a car using only spare parts from other cars.
ASLR (Address Space Layout Randomization) Randomizes where code, libraries, stack, and heap are loaded in memory. You can't just hardcode an address and jump there — you don't know where anything is. First need an information leak to discover the base address. Or use JIT spraying (fill predictable memory with your shellcode). ASLR is strong but not invincible — especially on 32-bit systems with limited entropy.
Stack Canaries A random value placed on the stack between local variables and the return address. If a buffer overflow overwrites the return address, it also corrupts the canary — the OS detects this and crashes the process before exploitation. Need an information leak to read the canary value first, then write it back during the overflow. Or find a way to overflow without touching the canary (like overwriting a function pointer instead).
KPTI (Kernel Page Table Isolation) A direct response to Meltdown/Spectre. Separates kernel page tables from user page tables so user processes can't speculatively read kernel memory through CPU side channels. Not really bypassable at the software level — this was a hardware vulnerability fixed by software. It just costs you some performance (about 5–15% slower syscalls).
CFI (Control Flow Integrity) The newest and strongest defense. At compile time, it builds a list of valid call targets. At runtime, every indirect call/jump is checked against that list. If you try to jump somewhere unexpected, the program crashes. Very difficult to bypass in practice. Requires finding corruptible data structures that influence control flow within the valid target list. Some attacks use "Call-oriented programming" — chaining only allowed call targets.

Think of it like a castle defense:

  • DEP is the moat — you can't just walk in
  • ASLR is the moving walls — every castle has a different layout
  • Stack canaries are tripwires — you step on one and alarms go off
  • KPTI is the reinforced floor — even if you get under the castle, you can't dig up
  • CFI is the guard checking every ID at every door

Modern exploits chain multiple bypasses together. You leak ASLR with a separate bug. You leak the canary with another bug. You build a ROP chain to get code execution. Then you find a kernel exploit to escape the sandbox. It's not one hack — it's a whole heist movie.

9. OS Security Fundamentals

User Accounts and Permissions

Every OS enforces who can do what. DAC (Discretionary Access Control) — used by Windows and standard Linux — lets file owners set permissions. You own a file? You decide who reads it. MAC (Mandatory Access Control) — SELinux, AppArmor on Linux — enforces system-wide policies that even root cannot override without authorization.

Relatable example: DAC is like letting everyone lock their own apartment door. MAC is the building security guard who also checks everyone at the front entrance. Even if you leave your door unlocked, the guard won't let strangers in.

Sandboxing and Isolation

  • Windows: AppContainer sandboxing (UWP apps), Windows Sandbox feature
  • macOS: App Sandbox (App Store apps), hardened runtime, entitlements
  • Linux: namespaces, cgroups, seccomp-bpf, flatpak/snap confinement, Docker containers
  • Android: Each app runs as its own user ID with its own sandbox. App A literally cannot see App B's files.
  • iOS: Strict sandboxing enforced by the kernel — apps cannot see each other's data. It's like each app lives in its own soundproof room.

Update Mechanisms and Patch Management

An OS is only as secure as its latest patch. Modern OSes have automated update pipelines:

  • Windows Update — cumulative monthly patches, out-of-band emergency fixes. Love 'em or hate 'em, those Wednesday patches keep the bad guys out.
  • macOS Software Update — system updates bundled with Safari and security patches
  • Linux (apt, yum, pacman) — package manager updates for kernel and userspace
  • ChromeOS — dual-root automatic updates with rollback protection. Update in the background, reboot once, done.

Real talk: That person who clicks "remind me later" for six months? They're the reason ransomware still works. Patch your stuff.

Secure Boot and Trusted Execution

  • UEFI Secure Boot — verifies bootloader signature before execution. No unsigned bootkits allowed.
  • TPM (Trusted Platform Module) — hardware-backed key storage, measured boot, attestation. Your computer's own vault.
  • Windows BitLocker / macOS FileVault / Linux LUKS — full-disk encryption tied to TPM. If someone steals your laptop, they get a paperweight.

Attack Surfaces by OS

OS Primary Attack Vectors

10. A Real Exploit Case Study: Dirty Pipe (CVE-2022-0847)

Let's make this concrete. In 2022, a researcher named Max Kellermann found a bug in the Linux kernel that let any unprivileged user write to any file on the system — even files they shouldn't have access to. It was called Dirty Pipe, and it's one of the most elegant privilege escalation exploits in recent history.

What it was: A race condition in how the Linux kernel handles pipes (the tiny data channels processes use to talk to each other). Under specific conditions, a process could write past the end of a page and modify data that was marked as read-only.

How it worked (simplified):

  1. The kernel uses "page cache" to buffer file data in memory
  2. Normally, pages that are mapped read-only in a pipe buffer are flagged — the kernel knows not to write to them
  3. The bug: under certain race conditions, the kernel forgot to check the flag. A process could splice a file into a pipe, then write past the pipe buffer boundary into the adjacent page cache page
  4. Result: writing to a file you don't own — including /etc/passwd to add a new root user

What it gave: Root-level arbitrary file overwrite on any Linux kernel from version 5.8 to 5.16.11. Affected everything — servers, desktops, Android devices, containers.

Why it matters: Dirty Pipe bypasses most defenses because it doesn't use memory corruption in the traditional sense. There's no buffer overflow, no ROP chain, no shellcode injection. It manipulates the kernel's own data structures through a race condition — something ASLR, DEP, and canaries can't protect against.

Proof of Concept (simplified):

/* Overwrite /etc/passwd to add a root user */
/* Run as any non-root user */

int fd = open("/etc/passwd", O_RDONLY);
int pipe_fd[2];
pipe(pipe_fd);

splice(fd, 0, pipe_fd[1], NULL, 1, 0);
write(pipe_fd[1], "pwned::0:0:::", 13);

/* Now: su pwned — no password required 🤯 */

The fix? A one-line patch. The kernel maintainer added a missing flag check. One line of code that, if missing, gives an attacker root access on millions of devices.

Lesson: The most dangerous vulnerabilities are often the simplest mistakes. And they live in the kernel — below everything else.

12. Final Thoughts

The operating system is the foundation of everything you do on a computer. Your applications, your network, your data — all of it sits on top of the OS. Your security is only as strong as the OS underneath.

Understanding how kernels work, how user mode differs from kernel mode, how memory is managed, and where attack surfaces exist makes you a better user and a better professional. Whether you're hardening a Linux server, analyzing a Windows exploit, or pentesting an embedded device, the same fundamentals apply.

  • Know your kernel architecture — it determines your blast radius. A monolithic kernel crash takes down everything. A microkernel crash takes down one service.
  • Understand privilege boundaries — every escalation exploit exploits them. User mode vs kernel mode is the most important line on your system.
  • Stay updated — the OS is the most patched piece of software on any machine. Dirty Pipe was one missing flag check. One line of code.
  • Choose the right OS for the job — there's no "best" OS, only the right one for your threat model. You wouldn't use Windows Server to run a smart fridge. Well, you could, but please don't.

The next time you click the power button, remember: a tiny piece of firmware wakes up, checks your hardware, loads a bootloader, hands off to a kernel, initializes the entire system, and presents you with a login screen — all in about 15 seconds. And somewhere in that chain, a single unchecked flag gave millions of users root access.

Remember: The OS is the ring below everything else. Trust it wisely, harden it thoroughly, and never stop learning how it works under the hood.

Stay sharp. Test responsibly. Patch thoroughly.
